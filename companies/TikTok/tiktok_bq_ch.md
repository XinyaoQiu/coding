### 测试

**写代码前**说：输入为空、输入非法。**写完后**逐个跑，报出中间变量的具体数字，不要只念逻辑。

| 类别 | 样例 | 抓什么 |
|---|---|---|
| 空 | `[]` `""` `[[]]` | 越界、`len(arr[0])` 崩 |
| 单元素 | `[x]` `[[x]]` | 循环只跑一次、`for i in range(1,n)` 不执行 |
| 全同 | `[1,1,1]` 全 1 矩阵 | 从没进过 if 分支的 bug |
| 无解 | 全 1（找 0）、有环（拓扑） | 返回 -1 的分支真的走到了吗 |
| 答案在首/尾 | `[0,1,1]` `[1,1,0]` | off-by-one |
| **非方阵** | `[[1,1,0],[0,0,1]]` (2×3) | **行列写反、`i*m+j` vs `i*n+j`** |
| 1×n / n×1 | `[[0,0,0]]` `[[0],[0],[0]]` | m、n 用混 |
| 非预期值 | `[0,1,2]`（以为只有 0/1） | `elif` 漏分支，该用 `else` |

**说法**："我系统地过一遍。先看结构——我的循环从 index 1 开始，所以验一下 n=1：___。然后空输入：___。然后无解的情况：___。最后答案在末尾的情况，off-by-one 一般在这里露出来。"

### 七条铁律

1. 超过 15 秒的沉默，前面必须有一句授权。
2. 解释不了的术语一个字都别说——他追问的永远是你说过的话。
3. edge case 在写码**之前**说，并留开口。
4. 被问"能不能更优"先想下界，敢站住；不确定就说"让我想一下"，**绝不猜一个复杂度**。
5. 复述题目那 30 秒是免费思考时间——嘴说套话，脑子想解法。
6. 写码中发现新 edge case 不扣分，**说法要归因于代码结构**，不说"我忘了"。
7. 交替，不是并行——想 20 秒 → 说出来 → 再想 20 秒。

### 主力故事一：premium 订阅系统

我讲一个我在 premium 订阅系统里做的东西吧。我负责的是把 Apple、Google 这些平台发来的订阅事件，同步成我们这边每个用户当前的订阅状态。用户订阅、续费、取消、扣款失败、退款到期，平台都是以事件通知的形式发给我们，我要根据这些事件把每个用户的状态维护对。我们这边状态用两个字段表示：一个 `status`，取值 paid / free / unsubscribed，客户端就读它判断能不能访问 premium；另一个 `paid_status`，取值 active / grace_period / billing_retry / cancel，记的是账单层面的细节。

我先铺一条完整的订阅生命周期，后面讲的问题都在这条线上。用户订阅，一段时间后某次扣款失败了、进宽限期，宽限期内 Apple 重试扣成功、恢复正常，后来用户自己把自动续费关了，到期，几个月后又回来重新订阅。这六步对应到状态就是 active → grace_period → active → cancel → expired → active。

这条线本身不难，难的是这六个通知到我这儿的时候，顺序是乱的、可能重复、还可能丢。所以核心挑战是：在这样一个不可靠的事件流上，怎么始终维持每个用户正确的状态。我下面按我当时踩坑的顺序讲，这套是怎么一步步长出来的。

最开始的实现很简单：收到通知，就读出这个用户的记录、根据通知算出新状态、写回去，先跑起来。

跑起来之后第一个撞到的是并发。看刚才那条线的第二步和第三步——扣款失败和重试成功，这两条通知可能只隔几秒，到我这儿几乎是同时的。如果两条同时进来，两个 worker 都读到同一份旧记录、各自算、各自写，后写的就把先写的覆盖了——经典的 read-modify-write 覆盖。而且这里还不只是"覆盖"这么简单：进宽限期要写宽限期的到期时间，恢复 active 要往后推订阅到期时间，两条通知改的字段集不一样，交错写出来的记录可能是哪条通知都不会单独产生的状态。这是钱，错了代价很大。所以我加了一个针对单个用户的分布式锁，用 Redis 的 SetNX 实现，key 就是用户 id，同一个用户的通知串行处理，不同用户之间互不阻塞。锁的 TTL 是 30 秒，同时我把 controller 的超时设成 10 秒——超时严格小于 TTL，就不会出现锁过期了但前一个 worker 还在跑的情况。

串行之后，第二个问题是乱序。就算我一条条处理，通知到达的顺序也不等于事件真正发生的顺序——平台不保证顺序，还会延迟、会重投。还是那条线，第三步和第四步：先是重试扣款成功，然后用户关掉了自动续费。如果这两条到达的顺序反过来，我按到达顺序处理，那条后到的续费成功会把已经写好的 cancel 打回 active——用户明明已经取消了，我们这边却显示还在订阅中，该给他的挽留提示也不会出现。所以我在每条记录上存一个"最后处理的事件时间"当水位线，新通知只有比这个时间更新才处理，旧的直接丢。这里的关键是拿什么时间去比——我用的是平台自己签名的那个事件时间，不是我们的接收时间，也不是数据库的更新时间。

接下来是更麻烦的一层，跨交易。看那条线的最后一步：用户到期之后隔了几个月又回来重新订阅。这时候 Apple 给的是一个全新的交易号——originalTransactionId 在一笔订阅的一生里是不变的，续费、宽限、恢复都是同一个，只有真的失效之后重新买才会换。

这就意味着光比时间不够了，我得先判断"这条通知说的到底是哪一笔订阅"。所以我先按交易号判归属：跟记录里存的一致，才按时间比新旧；对不上，说明是另一笔订阅。这里还有个边界：如果记录压根不存在，比如某条通知比订阅那条先到，那它没有主体可改，直接丢——规则是没记录的时候只有新订阅事件能创建记录。

不过跨交易这种归属判断，光靠我本地的时间戳是不行的。Apple 只保证同一笔交易内的事件时间有序，跨交易不保证——那是两条独立的订阅生命周期，时间戳没有可比性。而比错的后果是双向的：比错一个方向，一条已经作废的交易的订阅通知会把记录回退到死掉的那笔；比错另一个方向，用户真实的重新订阅会被当成旧事件丢掉——那就是用户付了钱拿不到权益。所以跨交易我干脆不比时间戳，交易号对不上的时候一律回调 Apple 的 subscription status 接口，让 Apple 直接告诉我当前哪一笔是 active 的，以它为准。等于把边界划清楚：同一笔交易内我信平台的签名时间，跨交易我只信平台的权威状态。这里 Apple 和 Google 有个有意思的差别：Google 的通知本来就只给一个 token，你必须回查它的 API 才知道状态；Apple 的通知虽然自带签名 payload，但在这种跨交易归属拿不准的场景，我同样选择回查 Apple、以平台的权威状态为准，而不是只信我手里这一条通知。

最后一个是重复。平台会重投通知，我这边一时没返回成功它就重发。这里有个容易想当然的地方：水位线其实一条重投都挡不住。因为重投是同一条通知，签名时间跟已经处理过的完全相等，而水位线的判断是"严格早于才丢"，相等会放行。我也可以把判断改成"早于或等于就丢"，但那样会误伤同一毫秒内的两条不同通知——丢一条真实事件比重复处理一条严重得多，所以我保留了保守的写法，另外做一层显式幂等。

幂等键用通知自带的唯一 id，放在 Redis，TTL 7 天——Apple 失败后会重试五次，间隔 1、12、24、48、72 小时，加起来差不多这么长。一个细节：这个键是**处理成功之后才写**，不是处理前占位。先占位的话，万一处理中途崩了，键留下来但状态没写，重投会被自己的键挡掉、那条通知就永久丢了；事后写最多重复处理一次，而重复处理算出来还是同一个状态。

所以整套演进下来，其实是四个正交的机制各挡一类问题：锁管并发、事件时间水位线管乱序、交易号身份加平台裁决管跨交易、UUID 幂等管重复。这套通知处理现在稳定支撑每天一千多条平台事件（Apple/Google/Stripe），而它维护出来的订阅状态，被下游高频读来判断用户是不是 premium，量级在千万级每天，走的是缓存优先的读路径。我觉得真正的难点不在任何单个机制，而在于意识到：我们完全依赖一个乱序、重复、延迟、还跨多笔交易的平台事件流，却要让每个用户的付费状态始终正确——这是个没有单点解法的系统性问题。

#### Follow-up 1：踩过什么坑？

水位线那块我踩过一个。一开始我拿来比的是数据库记录的更新时间——想着反正每次处理完都会更新，用它当水位线不是正好吗。

但这个时间记的是"我什么时候处理完的"，不是"这件事什么时候发生的"。而处理本身是有延迟的：通知从平台发出到我这儿处理完，中间可能隔了几十秒甚至更久。所以数据库里的更新时间永远晚于事件真正发生的时间，等下一条通知进来一比，它的事件时间反而"更早"，就被当成旧的丢掉了——**结果是新通知全被丢，状态卡在旧的上不动**。

修法是专门加了个字段，存平台自己在通知里签名的那个事件时间，拿它来比。这样比的才是事件真正发生的先后，跟我们处理得快慢、跟我们几台机器时钟对不对得上都没关系。

这个坑让我明白一件事：**判断顺序要用事件自带的时间，不能用我们观测到它的时间**。前者是事实，后者混进了我们自己系统的状态。

#### Follow-up 2：如果重新做，有什么会不一样？

会。而且不是补哪个功能，是**整套的一致性边界会画在不同的地方**。

先说现在这套的出发点：我当时想的是"同一个用户的一条通知，从头到尾必须是一个原子操作"。所以我拿一把锁把整段处理圈起来——读记录、幂等占位、算新状态、写库、删缓存、写审计，六件事都在锁里面。好处很直接：这一整段没有任何中间态会被别人看见，审计日志里的每一条 before/after 都是严格准确的，出了问题能一步步倒推。

但这个选择是有代价的。锁圈得这么大，就意味着我得依赖 Redis 可用、得给锁设 TTL、得处理 TTL 到期后另一个 worker 进来的情况、释放的时候还得用 Lua 校验是不是自己的锁——这些复杂度全是"我想把六件事绑在一起"带来的。

**如果重新做，我会从另一头出发：只让状态写这一件事是原子的，其它都放到外面去。**

具体来说，用 mongo 的条件更新——`findOneAndUpdate`，filter 里带上 `last_notif_event_time < 我这条的时间`，同时把通知的唯一 id 也写进这条记录。这一个操作同时做完三件事：判断这条通知是不是比已有状态更新、确认它没被处理过、然后写入。正确性由单文档的原子性保证，不需要锁。删缓存和写审计挪到这次更新之后，异步做。

**区别在哪**：现在这套是"先划一个互斥区间，区间里我想干嘛干嘛"；另一套是"不划区间，而是让那一次写本身携带所有判断条件，写成功就说明条件全满足"。前者是悲观的——先占住再说；后者是乐观的——直接试，条件不满足就自然失败。

**幂等那块也会跟着变。** 现在我用 Redis 存 notificationUUID，是因为它跟状态记录是两个东西、得单独找地方放。但如果判断已经下沉到那一次条件更新里了，唯一 id 就可以直接进 mongo——要么写在记录上，要么给审计表的 uuid 加唯一索引、让插入本身就是去重。这样审计表就一份数据两个用途：既是事后追溯的日志，又是线上的幂等键，不用再维护一套 Redis。

**那 trade-off 是什么？**

第一，**审计链会有缺口**。现在审计写在锁里，跟状态写绑死，要么都成功要么都不成功。挪出去之后，状态写成功、审计写失败是可能的，日志里会缺一条。对一个跟钱相关的系统来说，"我改了状态但没留下记录"是需要认真权衡的。

第二，**缓存不一致的窗口会变长一点**。现在删缓存在锁里，写完立刻删；挪出去之后中间隔了一小段，这段时间读到旧值的概率会高一些。不过这个影响有限，因为我们本来就有 TTL 兜底，真正在意实时性的读路径也是绕过缓存直接查库的。

第三点严格说不算 trade-off，而是**两套设计都改变不了的部分**：业务判断下沉不到数据库里。条件更新能表达"谁的时间更新"、"这条处理过没有"，但它表达不了"记录不存在的时候谁有资格创建"，也表达不了跨交易归属——后者得先回调 Apple 问当前哪笔是 active 的，这本来就是应用层的事，跟用不用锁无关（顺带一提，这个回调现在也是放在锁外面做的，因为它是跨公网调用，放进临界区会让锁的 TTL 取决于 Apple 的响应时间）。所以守卫这一层在哪套设计里都得留着，区别只是它从"锁保护下的一段逻辑"变成"条件更新之前的一层前置判断"。

**所以两套的分歧其实在最前面**：是先保证整段处理的互斥，还是先保证那一次写的原子。选前者你得到严格的可追溯性，代价是复杂度和对 Redis 的依赖；选后者你得到更少的依赖和更简单的失败模式，代价是审计和缓存要接受轻微滞后。我当时选了前者，是因为这是钱、我想要每一步都能倒查；但如果现在重新判断，我会认真考虑后者——尤其是当团队里已经有成熟的异步审计管线的时候，第一个代价就不成立了。

### 主力故事二：视频上传链路


我讲一个我做的内容平台相关的项目吧。我负责的是 UGC 内容从创作者提交、到经过我们的内容平台处理、内容审核、最后上线或者被拒下线的这一整套服务端链路，视频是其中一个主要的内容类型。

这套系统我会从两个角度讲，因为它的核心其实是一个内容平台加一套治理流程。

先说平台这块。我们有一个媒体平台服务，是所有内容的状态权威——不管是新闻、短帖、评论还是视频，都会在这里落一条元数据记录，记标题、URL、内容类型、当前状态、还有生成出来的 doc id 这些，视频的原始字节本身不存在这里，是在对象存储 S3 上。这个平台负责编排整个内容的生命周期：内容进来先落一个"处理中"的状态，然后异步地去做后续处理，处理完了再把状态推进到"已发布"或者各种失败态。

然后是内容怎么被处理和摄入的。我们有一个统一的内容处理平台,所有类型的内容最后都会被统一成一种"文档"格式,走同一条摄入管线,生成一个线上可服务的 doc、分配一个 doc id。我想强调的是这套是通用的、平台化的——视频只是其中一个内容类型,它跟一条普通帖子走的其实是同一条摄入和审核的流程,只是视频前面多了一步转码。转码本身是一个独立的视频平台在做,主要用 AWS MediaConvert 这个云转码服务,我们自己搭的 ffmpeg 只做兜底和生成缩略图,转好的多码率版本回到内容的元数据里,播放的时候按网络情况挑最合适的码率。

再说治理这块,这也是我觉得最能体现这套系统价值的地方。一个内容被摄入、生成 doc 之后,如果它还没被审核过,我们的平台会主动把它推去审核——push 到一个审核请求的消息队列里。审核那边有机审也有人审,判完之后,结论走另一条独立的消息队列回到我们平台,我们据此更新内容的审核状态;如果被判违规,就发拒绝通知、并且把这个内容下线、不再对外服务。所以审核这块是一个收发分离的设计:我们主动推请求,被动收结果,两条独立的队列。

除了内容审核,我还在上传入口写了一层反滥用的中间件——它会算请求 IP 的机器人评分、做限流,识别脚本刷量、异常上传这种行为。我当时特意把它设计成先观察、不硬拦的模式,先在真实流量上采集信号、验证阈值,确认不会误伤正常创作者,再考虑开启拦截。

用户那边,他们进"我的内容"页、或者下拉刷新的时候,客户端会来拉一次状态,我们这边是实时去媒体平台拿最新状态、不走缓存,因为这个页面对状态新鲜度最敏感,然后把平台内部的处理状态和审核状态,翻译成用户看得懂的展示——处理中、失败、审核中、已拒、还是已上线。

真正的难点,我觉得不在任何单个系统,而是这条链路跨了好几个系统、全程异步、而且每一步都可能失败:转码可能失败、内容摄入可能失败、也可能卡在处理中太久。所以我要保证的是,不管中间怎么失败,内容的最终状态对用户始终是清晰、正确的。我这里的处理是,所有能让内容失败的路径——转码失败、摄入失败、还有一个定时任务扫描卡太久的——都统一走一个带条件的原子更新:只有当内容当前还是"处理中"状态时才允许翻成失败态。这样不管哪条失败路径先触发,都只会生效一次,天然去重,而且绝不会把一个用户已经删掉的内容错误地复活。

所以整套东西的组织原则,一句话总结就是:一个统一的内容平台,加一个状态权威——所有内容类型统一处理、由一个中枢来编排从摄入到审核到上线下线的整个生命周期。这也是为什么我对这个 team 做的内容治理平台特别感兴趣,因为我做的正是这一类"把内容治理平台化"的事。
